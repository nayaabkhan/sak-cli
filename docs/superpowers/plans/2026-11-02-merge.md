# sak merge Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `sak merge -o <file>`, which combines the Switch base game, update and DLC in the current folder into one `.nsp` or `.xci`.

**Architecture:** Inputs are opened as lists of named byte ranges. Cnmt metadata from those ranges drives validation and version selection into a `MergePlan`. Format writers stream the planned ranges to `<output>.part`, then rename.

**Tech Stack:** Rust 2021; `clap` (derive), `anyhow`, `aes`, `cipher`, `ctr`, `xts-mode`, `sha2`, `rand`, `indicatif`, `fs2` (free space), `dirs`; dev: `tempfile`, `assert_cmd`.

**Spec:** `docs/superpowers/specs/2026-11-02-merge-design.md`

**Upstream source for reference:** clone https://github.com/julesontheroad/NSC_BUILDER at e9083e8. Paths below are under `py/ztools/`.

## Global Constraints

- Command: `sak merge -o <output.nsp|output.xci> [--keys <path>] [--force]`; no other options.
- Default keys path: `~/.switch/prod.keys`.
- Only `.nsp` and `.xci` inputs, matched case-insensitively, in the current folder only, not subfolders.
- `.nsz` and `.xcz` in the folder: error containing `not supported yet`.
- Never hold a whole NCA in memory; only headers and the cnmt section are read in full.
- Write to `<output>.part`, rename on success, remove `.part` on any error.
- Never print key values. Ship no keys or game data, in fixtures included.
- Exit 0 on success; non-zero with a one-line reason on failure.
- No Windows support, FAT32 splitting, title databases or extra flags.

## Review Focus

1. Re-running in the same folder, with the earlier output and a stale `.part` beside the inputs: neither is treated as input, so the merge succeeds. Test in Task 4.
2. The same NCA in two inputs, such as a base held both as an `.xci` and an `.nsp`, or an update also bundled in a multi file: identical title and version is deduplicated, not a "two base games" error. Test in Task 4.
3. A titlekey-encrypted NCA with no matching ticket: stop before writing and name the rights ID, rather than produce a file that won't launch. Test in Task 5.
4. Truncated or corrupt input (entry past end of file, bad magic, undecryptable header): one-line error naming the file, never a panic. Test in Tasks 2 and 3.
5. `-o` pointing to a missing folder, or to a read-only one: error naming the path, no partial output. Test in Task 5.

## Format facts

All integers are little-endian unless stated.

- **PFS0:** `PFS0`, u32 count, u32 string table size, u32 0; entries of 0x18: u64 data-relative offset, u64 size, u32 name offset, u32 0; string table. Generate like `gen_nsp_header`: names joined by `\0`, then pad with `0x10 - headerSize % 0x10` zero bytes (always 1 to 16), the padding counted in the string table size.
- **HFS0:** `HFS0`, u32 count, u32 string table size, u32 0; entries of 0x40: u64 offset, u64 size, u32 name offset, u32 hash region size, u64 0, 32-byte SHA-256 of the first hash-region bytes. Padded to a multiple of 0x200 (`gen_rhfs0_head`; zero padding is allowed when already aligned).
- **NCA header:** first 0xC00 bytes, AES-128-XTS with `header_key`, 0x200 sectors, tweak is the sector number big-endian in a 16-byte block. Plain fields: 0x200 `NCA3`; 0x204 distribution; 0x205 content type (1 = meta); 0x206 crypto1; 0x207 key area key index; 0x210 title ID; 0x220 crypto2; 0x230 rights ID (16 bytes); 0x240 four section entries of 0x10 (u32 start, u32 end, in 0x200 media units); 0x300 key area, 4 × 0x10; 0x400 section headers, 0x200 each: 0x4 crypto type (3 = CTR), 0x8 hash data, 0x140 u64 CTR.
- **Key generation:** `max(crypto1, crypto2)`; master index is `gen - 1`, or 0 when `gen` is 0.
- **Section CTR:** 16-byte big-endian counter: bytes of the header's CTR reversed in the high 8, `absolute_offset / 0x10` in the low 8. The key is key-area slot 2, decrypted by AES-ECB with the key area key.
- **Meta NCA:** section 0 is a PFS0 hash section. PFS0 starts at `section_start + hash_data.pfs0_offset` (u64 at section header 0x8 + 0x38) and contains one `*.cnmt`.
- **Cnmt:** 0x0 u64 title ID; 0x8 u32 version; 0xC u8 type (0x80 Application, 0x81 Patch, 0x82 AddOnContent); 0xE u16 extended header size; 0x10 u16 content count; 0x20 u64 extended field (the base title ID for Patch and AddOnContent); records at `0x20 + ext size`, 0x38 each: 0x20 hash, 0x10 NCA ID, 6-byte size, u8 type (6 = delta fragment), u8 ID offset.
- **Ticket:** u32 signature type at 0x0, which sets the body offset: 0x10000/0x10003 RSA-4096, 0x240; 0x10001/0x10004 RSA-2048, 0x140; 0x10002/0x10005 ECDSA, 0x80. Relative to the body: issuer at 0x0, 16-byte common titlekey at 0x40, type byte at 0x141 (0 common, 1 personalised, not supported), rights ID at 0x160. So an RSA-2048 ticket has them at absolute 0x180, 0x281 and 0x2A0.
- **Key derivation:** `titlekek_XX = ecb_dec(master_key_XX, titlekek_source)`. `key_area_key_application_XX`: `kek = ecb_dec(master_key_XX, aes_kek_generation_source)`, `src_kek = ecb_dec(kek, key_area_key_application_source)`, result `ecb_dec(src_kek, aes_key_generation_source)`.

**Files:**

- Modify: `src/nca.rs`, `src/lib.rs`

**Interfaces:**
- Consumes: `MergePlan`, `hfs0_header`, `NcaHeader`, `Keys::titlekek`
- Produces:
  - `nca::standard_header(header: &NcaHeader, titlekey: Option<&[u8; 16]>, keys: &Keys) -> Result<[u8; 0xC00]>`, re-encrypted
  - `titlekey_from_ticket(ticket: &Entry, master_index: u8, keys: &Keys) -> Result<[u8; 16]>`
  - `xci::write(plan: &MergePlan, keys: &Keys, out: &mut File, progress: &ProgressBar) -> Result<()>`, `xci::size(plan: &MergePlan) -> Result<u64>`

Port these from upstream rather than re-deriving them:
- Header fields and fixed values: `get_xciheader`, `lib/sq_tools.py:1144-1282`, plus `gen_rhfs0_head`, `Fs/Hfs0.py:435`.
- Fallback game info: `get_enc_gameinfo`, `lib/sq_tools.py:401`.
- Card size thresholds: `getGCsize`, `lib/sq_tools.py:327`.
- Header rewrite: `get_newheader`, `Fs/Nsp.py:5833`.

Header rewrite: set 0x204 to 1, zero the rights ID, and for titlekey NCAs put the decrypted titlekey into all four key-area slots, ECB-encrypted with the key area key (`titleKeyDec * 4`, as upstream), then re-encrypt 0xC00 bytes with `header_key`. The NCA body is copied unchanged from 0xC00. Each HFS0 hash covers the first 0x200 bytes, unchanged by the rewrite since only the signature sector is hashed, so it can be taken from the source. Only NCAs go into `secure`, not tickets or certs.
